# 任务规划（执行清单）

按顺序做。每个任务都有**产出**和**验收标准**，验收不过不要进下一个。
标 `🔶可选` 的可以跳过，标 `⭐关键` 的做砸了后面会一直疼。

进度总览：

| 阶段 | 任务 | 目标 | 预估 |
| --- | --- | --- | --- |
| 奠基 | T0–T2 | 项目骨架 + 数据层 | 1–2 天 |
| 内核 | T3–T5 | 能跑的战斗模拟（无 UI） | 3–5 天 |
| 可玩 | T6–T9.5 | 第一个能玩的版本（战士单职业） | 5–7 天 |
| 完整 | T10–T14 | 三职业 + 全系统 | 1–2 周 |
| 打磨 | T15–T18 | 平衡、体验、分发 | 按需 |

## 阶段一：奠基

### T0 — 工程骨架 ⭐关键

**做什么**

```bash
cargo new --name tui-game .
# 改成 workspace，建三个 crate
cargo new --lib crates/game-data
cargo new --lib crates/game-core
cargo new --bin crates/game-tui
```

根 `Cargo.toml`：

```toml
[workspace]
members = ["crates/*"]
resolver = "2"

[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
# ... 把 01-tech-stack.md 的依赖都放这里，子 crate 用 workspace = true 引用
```

还要做：
- `.gitignore`（`/target`、`*.log`、`saves/`）
- `rustfmt.toml`、`clippy.toml`
- `git init` + 首次提交

**产出**：`cargo build` 通过的空 workspace。

**验收**
- [ ] `cargo build --workspace` 通过
- [ ] `cargo clippy --workspace -- -D warnings` 无告警
- [ ] `game-core/Cargo.toml` 里**没有** `ratatui`/`crossterm`

### T1 — 数据类型定义

**做什么**

在 `game-data` 里按 `04-data-schema.md` 定义所有 `*Def` 结构体和枚举，全部 `#[derive(Debug, Clone, Serialize, Deserialize)]`。

重点：
- ID newtype：`MonsterId(u32)`、`ItemId(u32)`、`SkillId(u32)`、`MapId(u32)`、`NpcId(u32)`
- `Range { min: i32, max: i32 }`，带 `fn roll(&self, rng) -> i32`
- `GameData` 容器：`Vec<MonsterDef>` + `HashMap<String, MonsterId>`（slug → id）

**产出**：编译通过的类型定义，还没有加载逻辑。

**验收**
- [ ] 所有 schema 文档里的字段都有对应 Rust 字段
- [ ] `cargo doc --open` 能看到每个公开类型有一行文档注释

---

### T2 — RON 加载与校验 ⭐关键

**做什么**

1. `GameData::load(dir: &Path) -> Result<GameData, DataError>`
2. 两遍加载：先全部读入并建 slug 表，再解析所有交叉引用
3. 实现 `04-data-schema.md` 末尾那份完整校验清单
4. 错误类型用 `thiserror`，**每条错误都带文件名 + 条目 ID + 建议**
5. 写一个最小数据集：3 只怪（鸡 / 鹿 / 多钩猫）、5 件物品、1 张地图（比奇省）、1 个 NPC

**产出**：`data/` 目录下有能加载成功的最小内容集。

**验收**
- [ ] `GameData::load("data")` 成功
- [ ] 故意把掉落表里的物品 ID 改错 → 报错信息指明文件、条目、错误 ID
- [ ] 故意造一个地图循环依赖 → 报出环路径
- [ ] 单元测试覆盖至少 6 条校验规则（每条一个 `#[test]`，用内联 RON 字符串，不读文件）

> 💡 这一步做扎实了，后面写内容表时会快很多；偷懒的话每次加怪都要靠 panic 调试。

## 阶段二：内核（无 UI，全靠测试驱动）

> 这个阶段**一行 UI 代码都不写**。目标是先有一个数值正确、可测试的模拟器。
> 验证手段是 `cargo test` 和一个输出纯文本的调试 binary。

### T3 — GameState 与属性系统

**做什么**

```rust
pub struct GameState {
    pub version: u32,
    pub class: Class,
    pub gender: Gender,               // ADR-006，创建后不可改
    pub high_risk: bool,              // ADR-002，创建后不可改
    pub level: u16,
    pub exp: u64,
    pub hp: i32, pub mp: i32,
    pub base: BaseStats,              // 等级带来的裸属性
    pub equipment: [Option<ItemStack>; SLOT_COUNT],
    pub inventory: Vec<ItemStack>,
    pub skills: BTreeMap<SkillId, SkillProgress>,
    pub current_map: MapId,
    pub map_kills: BTreeMap<MapId, u64>,
    pub combat: Option<Combat>,
    pub stats: LifetimeStats,          // 累计击杀 / 金币 / 掉落，给统计面板
    pub pity: BTreeMap<(MonsterId, ItemId), u32>,  // ADR-004 保底计数器
    pub tick_count: u64,
    rng: Pcg64,
    #[serde(skip)]
    derived: OnceCell<DerivedStats>,   // 缓存
}
```

实现：
- `fn derived_stats(&self, data) -> &DerivedStats`：裸属性 + 装备 + buff 汇总，带缓存
- `fn invalidate_derived(&mut self)`：换装 / 升级 / buff 变化时调用
- 职业成长表（每级 +HP/+MP/+DC 等）放 `balance.ron`

**验收**
- [ ] 穿上一件 `攻击 (10,25)` 的武器 → `derived.attack` 正确增加
- [ ] 脱下装备 → 属性回落
- [ ] `invalidate` 漏调会被测试抓到（写一个「换装后立即读属性」的测试）

### T4 — 战斗循环 ⭐关键

**做什么**

按 `03-game-design.md` 的公式实现：

```rust
impl GameState {
    pub fn tick(&mut self, data: &GameData) -> Vec<GameEvent>;
}
```

tick 内部顺序（**顺序很重要，固定下来别随意改**）：

1. 结算持续效果（中毒、药水持续回血）
2. 检查死亡 / 休息状态
3. 自动喝药判定
4. 如果无战斗 → 刷怪判定
5. 玩家出手判定（技能优先于普攻）
6. 怪物出手判定
7. 怪物死亡结算（经验、掉落、击杀计数）
8. 升级判定（可能连升多级 → while 循环）
9. `tick_count += 1`

**验收**
- [ ] 固定种子，Lv.1 战士在比奇省跑 1000 tick → 不 panic，HP 不为负，经验单调不减
- [ ] 怪物防御 ≥ 玩家攻击上限 → 产生 `Blocked` 事件，伤害恒为 0
- [ ] `proptest`：随机属性组合跑 1000 tick 不 panic、不溢出（用 `i64`/饱和运算）
- [ ] 同一种子跑两次 → 事件序列完全一致（确定性测试）
- [ ] 保底生效（ADR-004）：把某稀有掉落设为 `chance: 0.001`，固定种子跑到第 3000 次击杀 → 必得

---

### T5 — 调试 CLI + 快照测试

**做什么**

1. `crates/game-tui/src/bin/sim.rs`（或单独 `examples/sim.rs`）：

```bash
cargo run --bin sim -- --class warrior --ticks 36000 --seed 42
# 输出：最终等级、属性、累计金币、击杀分布、掉落清单、每小时经验
```

2. `insta` 快照测试：固定种子跑 N tick，快照最终状态摘要
3. `criterion` 基准：测 `simulate_offline(12h)` 耗时

**产出**：一个能在终端里"看数值曲线"的工具 —— 后面所有平衡调参都靠它。

**验收**
- [ ] `sim` 能跑 1 小时模拟并输出可读报告
- [ ] 快照测试建立，`cargo insta review` 流程走通
- [ ] 12 小时离线推演 **< 500ms**（见 `02-architecture.md` 的性能约束）

> 💡 **这一步是整个项目的分水岭。** 做完之后你可以在没有任何 UI 的情况下调整整个游戏的平衡性，而且改公式时快照会立刻告诉你影响面。

## 阶段三：可玩版本（战士单职业）

### T6 — TUI 骨架与主循环

**做什么**

1. 终端初始化 / 恢复（`enable_raw_mode`、`EnterAlternateScreen`），**务必装 panic hook 恢复终端**（否则 panic 一次终端就废了，要重开 shell）
2. 按 `02-architecture.md` 的累加器实现主循环
3. 布局：按文档里那张 ASCII 草图搭出角色 / 战斗 / 日志三个面板
4. `tracing` 初始化到文件
5. `Q` 退出、`Ctrl+C` 安全退出
6. 最小终端尺寸检查

**验收**
- [ ] 跑起来能看到战斗日志实时滚动
- [ ] 主动 `panic!()` 测试 → 终端状态正常恢复，报错可见
- [ ] 窗口缩放到 40×10 → 显示提示而不是崩溃
- [ ] CPU 占用空闲时 < 2%（挂机游戏会开一整天，这条很重要）

**做什么**

- `theme.rs`：品质颜色、HP/MP 条颜色、事件类型颜色
- 进度条 widget（HP / MP / 经验），支持中文标签

**验收**
- [ ] 中文装备名在面板里对齐无错位

### T8 — 面板：背包 / 装备 / 技能 / 地图

**做什么**

四个可切换面板（`1`–`4`）：

| 面板 | 功能 |
| --- | --- |
| 背包 | 列表 + 选中详情、穿戴、使用、丢弃、批量卖垃圾 |
| 装备 | 10 个槽位、对比当前 / 候选装备的属性差（`+5 / -2` 彩色标注） |
| 技能 | 已学技能 + 等级 + 自动释放开关 |
| 地图 | 地图列表、解锁条件、当前进度、切换 / 自动推进开关 |

交互统一用 `↑↓` 选择 + `Enter` 确认 + `Esc` 返回。

**验收**
- [ ] 能在 UI 里完成"打到装备 → 看到对比 → 穿上 → 属性变化"全流程
- [ ] 所有操作走 `GameState::apply(Command)`，UI 层**不直接改状态**（这条要自查）

---

### T9 — 存档（多槽位）与离线收益

**做什么**

按 ADR-001，存档是**槽位目录**而不是单文件（结构见 `02-architecture.md`）。

1. `SaveSlot` 抽象：槽位 ID 生成、目录布局、`characters.json` 索引读写
2. 原子写存档（tmp → fsync → rename），`.bak` 回退
3. 自动存档计时器 + 退出存档
4. 启动时算离线时长 → `simulate_offline` → 弹窗展示 `OfflineReport`
5. 存档版本迁移框条（即使现在只有 v1，也把迁移链的壳搭好）
6. `characters.json` 损坏时能通过扇描 `slots/` 重建

**验收**
- [ ] 退出再进 → 进度完整保留
- [ ] 手动改存档 `last_saved_at` 往前推 2 小时 → 重进看到合理的离线报告
- [ ] 把存档文件截断一半 → 自动用 `.bak` 恢复，不崩溃
- [ ] 删掉 `characters.json` → 下次启动能从 `slots/` 重建出完整列表
- [ ] 改系统时间往前调 → 离线时长不为负、不刷奖励
- [ ] ⭐ **开两个角色，分别挂 1 小时，确认未载入的角色没有产生离线收益**（ADR-001 的核心约束）

---

### T9.5 — 角色列表与创建流程

**做什么**

1. 启动后的角色列表界面：名字 / 职业 / 等级 / 最后游玩时间 / 高风险标记
2. 创建角色：职业 → 性别 → 名字 → 高风险模式开关
   - 这三项（职业 / 性别 / 高风险）**创建后不可更改**，UI 要明确告知
   - 高风险模式要说清代价（掉落 +50%，死亡掉装备）
3. 删除角色：**输入角色名**确认（不是简单 y/n，这是不可恢复操作）
4. 名字校验：长度、字符集、**允许重名**（槽位目录用生成 ID，不用名字）

**验收**
- [ ] 能创建两个同名同职业的战士，互不干扰
- [ ] 删除其中一个 → 另一个完全不受影响
- [ ] 角色名输中文 → 列表对齐正常（复用 T7 的 `pad_to`）
- [ ] 高风险角色在列表里有显著视觉标识
- [ ] 试图穿戴异性装备 → UI 说明原因（而不是默默置灰）

> 🎉 **到这里你有一个能玩的游戏了。** 建议在这里打个 tag，然后真的挂机玩两小时，记下所有觉得难受的点，再往下做。

## 阶段四：完整系统

### T10 — 法师与道士

**做什么**
- 法师：MC 伤害、MP 瓶颈、群伤技能（对多怪地图收益）
- 道士：SC、治疗、毒 debuff、召唤物作为第二战斗单位
- 召唤物需要扩展 `Combat` 结构（宝宝有自己的 HP / 攻击 / 攻击间隔 / 存活时间）
- 三职业各自的技能树数据

**验收**
- [ ] 三职业各跑 1 小时 `sim`，每小时经验在同一量级（差距 < 30%）
- [ ] 法师在"无魔法药"状态下行为合理（不会卡死循环）
- [ ] 召唤物死亡 / 重召的状态机无泄漏（跑 10 万 tick 内存稳定）

**做什么**

**验收**
- [ ] 挂机 1 小时金币收支为正（否则经济系统失衡，回去调 `balance.ron`）

### T12 — 武器升级（赌博系统）

**做什么**

UI 上要有**明确的成功率显示和二次确认**（会碎武器的操作绝不能手滑触发）。

**验收**
- [ ] 升级 10000 次的蒙特卡洛测试 → 实际成功率与配置误差 < 1%

## 执行建议

1. **严格按 T0→T18 顺序**，尤其不要跳过 T5 就去写 UI。见过太多项目在 UI 上花两周，最后发现数值系统全是漏的。
2. **每个任务一个 git 分支 / 至少一个独立提交**，提交信息写清楚"做了什么 + 验收通过"。
3. **T9 完成后先玩**。你自己玩两小时得到的反馈，比继续闷头做五个任务更有价值。
4. **内容填充（T15）随时可做**，累了就去加几只怪，比调公式轻松。
5. **设计决策记在 `doc/decisions.md`**（ADR 格式）。已有 7 条拍板记录，后续新决策追加到那里。

现在就可以开始 **T0**。需要我直接把 T0 和 T1 的代码搭出来吗？
